# The PR impact report: syntactic head revisions, one revocable comment, a deterministic graph result

Status: accepted. Builds on [ADR 0008](0008-team-granted-repository-visibility.md) (the narrow PR comment, the GUI report behind a link, recompute on narrowing, private impact notices), [ADR 0011](0011-aggregated-budgeted-decisive-payloads.md) (budgeted, aggregated shapes) and [ADR 0012](0012-shard-layout-and-incremental-indexing.md) (complete revisions, the blob cache, publish sequences), and amends ADR 0008, [ADR 0009](0009-human-login-agent-binding-forge-sync.md) and ADR 0012 where stated. Moves CR-head indexing from a post-v1 question (RFC 0001 §11 Q6) into the plan, and makes Yggdrasil write to Forges for the first time.

The report answers one reviewer question: what breaks if this Change Request merges now. It is deterministic and graph-derived, with no model opinion. The [forge research](https://github.com/randax/yggdrasil/blob/5fcd7d45db11042a5f49cf2f396b317575f97d9f/docs/research/pr-impact-forge-apis.md) found that most of it needs no head data: callers, owners and Memory staleness come from base Shards plus the changed Symbols. Head data matters for edges, Symbols and exports the CR adds or removes, and for agents reviewing the CR. ADR 0012 makes a head cheaper to build: unchanged files come from the per-blob cache, though resolution, segment build and upload stay proportional to the repo.

## The decisions

### Each CR head is a complete syntactic revision under its own pointer

A CR head is built as a complete Shard revision of the head commit, as ADR 0012 builds the default branch, and published under a per-CR pointer instead of the repo's pointer. It is never the repo's current revision: it runs no Memory staleness checks and writes no cross-repo rows, so other repos never see a head's references.

Heads get no precise pass: it would cost about 4 worker-minutes per push (around 67 worker-hours a day at 1,000 pushes, a fifth of the fleet budget) and would run build code on every push. A head reuses ADR 0012's stored precise output for every Precise Root that passes ADR 0012's full reuse test (input hash, outside-file hashes, and expiry for roots without a lockfile); when a reused output expires, the head is recomposed with that root syntactic, as the default branch is. Every edge carries its Provenance.

This amends ADR 0012 for per-CR pointers:

- **Publication.** Each CR pointer has its own desired generation, bumped by every push, force-push, retarget, close and reopen, and its own lease; heads never take the repo's lease and skip pre-warm. A head swap is a compare-and-swap on that generation and on the head revision it expects to replace, so a build that finishes after a newer push, a close, an eviction or a newer build of the same head (after a Precise Root expiry or a schema or policy rebuild) never publishes. A head swap takes a publish sequence value like any swap.
- **GC.** Every live or pending CR pointer is a GC root. An incarnation's retention starts when the last pointer referencing it retires it (a push, eviction, idleness or close), and then ADR 0012's retention rules apply.
- **Cursors.** A `cr:` cursor pins the head revision and the publish sequence, like any cross-repo cursor.
- **Schema and policy bumps.** Live heads are rebuilt after a bump, queued below default-branch rebuilds; until then a head is pending.
- **History.** A head's history facts are the facts reachable from the merge-base plus `git log <merge-base>..<head>`, so `history` on a head lists only commits in the head's own ancestry.
- **Head-scoped facts.** Each head revision carries, as a manifest-listed object that is never served, its own exports, references and package facts. A request that reads a head overlays these for the CR's repo, privately to that request; every hop into the CR's repo reads the head, except where the graph result below reads the default revision for removed and changed Symbols, so a response never mixes the two silently, and `deps`, `dependents` and re-export chains reflect the CR.
- **Change set.** The merge-base side comes from a facts-only build of the merge-base tree: per-file facts from the blob cache, plus the repo-wide export resolution that `export *`, `__all__` and export maps need, with no segments built or uploaded. The change set (Symbols added, removed, moved, signature-changed and body-only-changed; exported keys added, removed and redirected; the fingerprints Memory prediction needs) is stored as its own object keyed by (head revision, merge-base commit), outside the head's manifest, so a merge-base move replaces the change set without republishing the head. It is kept while its head pointer references it, then for the retention window. Query nodes read it, so the GUI report needs no mirror or blob cache. After every default-branch publish, a worker checks the merge-base of each live head of that repo; until a moved merge-base's change set exists, readers see the previous one, labelled with the merge-base it used.

### Which CRs, the limits, and the lifecycle

- Every open CR that targets the default branch of an admitted repo is eligible, drafts and fork CRs included: nothing on a head runs code. An Admin can turn the report off per repo.
- The poll loop lists open CRs per repo on its own conditional request, independent of default-branch changes, so opens, pushes, force-pushes, retargets, closes and reopens are seen without webhooks; webhooks only make it faster. Eligibility changes bump the CR's generation.
- Only a CR's newest push is built. Head builds queue below default-branch jobs, so they never cost the syntactic freshness target. Within the head queue, CRs by human authors with write access or a linked Member come first, bot accounts (Forge Apps and bot users such as dependency updaters) next, others last, so a flood of outside or bot CRs cannot starve the rest.
- A repo keeps at most 50 live heads: 30 reserved for human authors with write access or a linked Member, at most 10 for bot accounts, and the rest for anyone; within each class the most recently pushed win. From the GUI report of a non-resident open CR, a Member can request a rebuild (an explicit action, never a side effect of opening the page) into a separate pool of at most 10 per repo that lapses after a day, rate-limited per Member, so a GUI read never evicts a resident head. A CR idle for 30 days loses its head until its next push. A CR changing more than 5,000 files gets no head. An Admin can change all three.
- A head revision inherits its base repo's Visibility.

| Head state | Comment | Status | GUI report | head `revision` |
|---|---|---|---|---|
| pending (queued, building, awaiting rebuild) | unchanged, or none yet | none yet | "being built" | `head_unavailable` (pending) |
| live | current report | success | computed at read time | served |
| not resident (evicted, idle) | edited once to fixed text ("no longer updated; it returns when the CR is next analysed"); withdrawn on narrowing at once | unchanged | "not resident"; opening it queues a rebuild | `head_unavailable` (not resident) |
| too large | "too large to analyse: N files changed" | success | the same notice | `head_unavailable` (too large) |
| closed or merged | left as is; withdrawn on narrowing | unchanged | "closed"; no report | `head_unavailable` (closed) |
| no longer eligible | deleted | unchanged | "not eligible" | `head_unavailable` (not eligible) |

### What the graph result is a function of

The merge-base is computed between the head and the target commit of the default revision current at the pinned publish sequence. When histories criss-cross and there are several best common ancestors, the change set is computed against each; if they differ, the report says the impact is undetermined. If a shallow mirror lacks the merge-base, the worker deepens the mirror; if it still cannot be established, the report says the impact is undetermined, never zero.

The graph result is the `impact` Verb seeded with the CR's change set (RFC 0001 §7): the changed, moved and removed Symbols and the removed, redirected or newly colliding exported keys (an added key that another visible repo already exports changes its consumers' candidate sets, so they are compared before and after). Seeds are taken in id order and share one work cap, expanded breadth-first in turn and deduplicated, with continuation by cursor, so a seed with many callers cannot crowd out the others. For removed, moved and signature-changed Symbols, same-repo callers and tests come from the default revision at the pinned sequence, minus call sites in files the CR changes, plus the head's own callers, because the merge will keep callers added on the default branch since the CR branched; removed Symbols are seeded by their default-revision ids. Other same-repo impact comes from the head, and other repos' from their current default revisions at the pinned publish sequence. The result is computed under the comment's ceiling or the reader's effective view. Counts follow ADR 0011: when a work cap stops discovery, a count says "at least N". Its inputs are the change set, the publish sequence, the ceiling or view, the ownership facts (CODEOWNERS from the Shards; Team membership and Admin ownership rules, with the control-plane generation that changes them) and the budget. Identical inputs give an identical result: it is ordered totally (ranking keys, then repo and Symbol ids), snapshot-tested on fixture repos, and an unchanged result is never reposted.

The Memory part is not cached or shared. On each GUI read it is projected for that Member with ADR 0008's ordinary rules (Audience, private overlay, lifecycle, suppression, every anchored repo in view, counts included). A Memory is predicted to go stale when the CR changes, moves or removes an anchored Symbol, File or Doc Section (a move gives a Symbol a new id, so its Memories would be flagged removed) and the default branch has not changed that node since the merge-base: the head's content is then compared with the Memory's latest baseline (its latest affirmation, otherwise its original fingerprint). Where the default branch has also changed the node, the prediction is shown as undetermined.

Each computation of a CR's report takes the next value of a per-CR computation counter, and a Forge write is accepted only for a computation newer than the last one written, so an older computation finishing last is dropped. The report is recomputed on every push; on ADR 0008 narrowing; when the merge-base moves; and on drift, at most hourly per CR, only when a revision it read or a key it looked up has changed (ADR 0012's cached-result rule), and posted only when the ceiling-filtered result itself differs. A change seen only outside the ceiling produces no Forge write. The comment states the head sha and "unchanged since" the time its visible content last changed.

### What the report contains

Each changed Symbol is classified as added, removed, signature-changed or body-only-changed. Alongside ADR 0007's fingerprint of the normalised defining span, which stays the staleness fingerprint, each Symbol gets an interface hash, defined per kind from the tree-sitter parse: a function's or method's declared signature; a type's declaration with its public members (fields, variants, method signatures); a constant's declaration and declared type. "Body-only" is shown as "signature syntactically unchanged", because an inferred return type can change under a body edit. Symbols moved to another path are classified as moved when exactly one old Symbol matches, by exported key first and fingerprint second; when no unique match exists, or the two disagree, the change is reported as a removal plus an addition. A move is shown as a move, not a break, but counts as a removal for Memory prediction. The interface hash rides the M1 schema bump with ADR 0012's changes.

The exported surface is diffed too: exported keys (bindings, aliases, re-exports, package export maps, specifiers) between merge-base and head. Removing `export { foo }`, a name from `__all__` or a `pub use` breaks consumers without changing any declaration, so a removed, redirected or newly colliding key seeds the caller search.

Sections, in order:

1. **Summary:** counts of Symbols and exported keys changed by class, and of repos, owners and tests affected.
2. **Changed exported API:** removed or redirected exported keys and signature-changed or removed exported Symbols, first because they break callers.
3. **Cross-repo callers and dependents:** grouped by repo, ranked by caller count and then Provenance, then by ids, aggregated as ADR 0011 requires (a precise caller says so; an ambiguous one shows "1 of N"), with breaking-change impact ahead of body-only impact.
4. **Affected tests** per repo, through `TESTS` edges.
5. **Owners** of the affected code, by name and without @-mentions: mentions notify irrevocably, and reaching people belongs to the notification plumbing. The comment names only owners taken from CODEOWNERS files in repos inside its ceiling; Team names and ownership by Admin rule are control-plane facts and appear only in the GUI report.
6. **A truncation notice and the GUI link.**

The comment applies this to ADR 0008's narrow ceiling, with a default budget of about 1,500 tokens and truncation always stated. The GUI report applies it to the signed-in Member's effective view at read time, adds the Memory predictions, and lets the Member browse the head graph.

### Private impact notices for hidden impact

ADR 0008's private notice pass runs separately from the report, asynchronously, and is never ordered before or after any Forge write, so the comment's timing reveals nothing. It runs once per head sha, as if the CR's author were the caller; an author with no linked Member is treated as a caller whose view is the comment's ceiling, since they can already read the CR's own repo on the Forge (this amends ADR 0008's "only the Forge-public set"). A CR with no head (too large, over the cap, idle) gets a diff-only pass that maps its changed hunks onto the default revision's Symbols, so it still notifies. The pass runs again on drift only when the set of hidden affected repos changes. Notices keep ADR 0008's recipients and its per-change, per-day dedup. Notices caused by CRs from authors without a linked Member are rate-limited per CR repo, and those over the limit are coalesced into one daily digest per recipient, never dropped, so throwaway accounts cannot flood Owning Teams or hide a real notice.

### Where it is posted

**Forge-public** is the one definition ADR 0008 and [ADR 0010](0010-ask-agent-and-chat-adapters.md) use: an admitted, Open repo whose code anyone on the internet can read. That is a public repo, with its repository feature open to everyone, on github.com, gitlab.com or codeberg.org, or on a self-managed Forge whose connection an Admin has attested as world-readable (off by default). Internal repos never count, and a public repo an Admin made Restricted is not Forge-public. A comment draws only on Forge-public repos plus the CR's own admitted repo. Forge visibility is read at sync and checked again before each post; if the Forge cannot answer, the repo is treated as not Forge-public for new posts. A lapse of Forge-derived state past ADR 0008's maximum age freezes comments that drew on the lapsed repos (no edits, no reposts) until visibility is known again, then they are reconciled; a lapse alone is not evidence of narrowing, so it triggers no deletions. This amends ADR 0008's lapse rule for existing PR comments only; new posts and every other ceiling still treat a lapsed repo as not Forge-public.

**The comment.** One per CR, identified by its stored Forge comment id, never by author. Before each Forge write, the control plane records the write's intent and the repos the new revision draws on, with an outcome of unknown; the Forge's answer marks it published or rejected. The record for a comment is the union over every published or unknown revision since it was last deleted, because Forges keep edit history readable; an unknown outcome is reconciled by reading the comment from the Forge before any withdrawal decision, and treated as published if it cannot be. Each intent is appended to an object-storage log under its own prefix, which restores never roll back (like RFC 0001 §5.1's Memory log), before the Forge write is sent, and its outcome after, so a restored database replays it and still finds every comment it must withdraw, open or closed. Every comment body carries a hidden marker with the deployment, CR and intent identity; it is used only to resolve an unknown create when re-listing the CR's comments written by the reporter's own credential, and to confirm a withdrawal is complete. While the restore gate is closed (RFC 0001 §5.1), the reporter sends no Forge writes except withdrawals and runs no notice passes; it replays the log and completes the resulting withdrawals before normal reporting resumes. While a result is no narrower, the comment is edited in place. When access narrows (ADR 0008) for any repo in that union, the whole comment is deleted at once, whatever the head's state, never edited into a withdrawal; an open CR with a live head then gets a fresh comment, and any other CR a new comment with fixed text saying the report was withdrawn.

**Ordering.** Writes for one CR are serialised under a per-CR write lease and fenced by the CR's generation and an authority generation that every narrowing bumps (a repo leaving Forge-public or Open, an un-admission, a change to the reporter's ceiling). A write computed under an older generation is dropped. A withdrawal is complete only once in-flight writes have resolved and the bot's comments have been re-listed from the Forge. Withdrawals go ahead of every other write in the installation's queue.

**Reconciliation and failure.** Before creating a comment the reporter checks the stored ids and its pending intents for the CR, so a create whose response was lost is not duplicated. A comment a human deleted is not recreated for the same head sha. A failed write or delete is classified: transient failures (rate limits, timeouts) are retried with backoff; permanent ones (an archived repo, a revoked installation, a credential that no longer owns the comment, a locked conversation) are not retried and surface at once. Admin status lists every comment whose withdrawal is overdue or impossible, so an Admin can remove it by hand. Copies already delivered by Forge email notifications cannot be withdrawn; that residue is accepted, as for chat answers in ADR 0008.

**The commit status.** Posted on GitHub with context `yggdrasil/impact (#<n>)`, state `success`, fixed text ("Impact report") and the GUI link, once the report is first posted. It carries nothing derived from impact, so its unrevocable history leaks nothing, and it is never pending or failing. The documentation tells repo admins not to make it a required check, and, because a write credential that can post statuses could post `success` under any context, to pin every required check to the app expected to set it. On GitLab and Forgejo a status needs a credential that can push code, so it is off by default; an Admin can enable it per connection. On GitLab it is posted only on same-project merge requests (it appears as an external pipeline job, an accepted effect of enabling it); fork merge requests are skipped, not retried.

**The GUI link** is `/cr/<forge-id>/<remote-repo-id>/<n>`, keyed by immutable Forge identity, the same whether or not anything lies beyond the ceiling. The route checks visibility first: a reader without a session gets the same login redirect as every GUI path ([ADR 0014](0014-web-gui-stack.md)), and for a signed-in Member a repo outside their view and a CR that does not exist get the same not-found, before any head state, file count or rebuild is revealed or offered.

**The reporter** is a built-in server principal, like ADR 0008's notice pass: its own view is every admitted repo, and everything it posts is computed under the comment's ceiling, enforced by the server. It is not an Admin-issued Service Agent and needs no Team grants, so a Restricted repo's own CR is reported without a widening. This amends ADR 0008's description of the reporter as a Service Agent with an adapter credential and ADR 0009's list of Service Agents.

**Write credentials** are separate from sync credentials, at least privilege, and optional per Forge connection (this amends ADR 0009's read-only credential list):

- **GitHub:** a second GitHub App, separate from the sync App, with Issues write (CR comments use the issues endpoint) and Commit statuses write, using one-hour installation tokens. The sync App keeps its read-only permissions, so its key never mints write tokens.
- **GitLab:** a project or group access token with the Reporter role, which can comment but not push (Premium or higher on GitLab.com), or a dedicated bot user's token on self-managed Free. A token's comments belong to its bot user, so it is renewed through GitLab's rotate API, which keeps the same user, and admin status warns before it expires; replacing it with a different token first withdraws its live comments or needs a Maintainer to remove them.
- **Forgejo and Codeberg:** a bot user's token with `write:issue`, limited to the repos it serves.

A connection without a write credential still gets head revisions, the GUI report and `cr:` Verbs; nothing is posted.

### Head revisions in the Verb contract

Graph Verbs accept `revision: {repo, cr: <n>}`, bound to the base repo's identity: `node`, `neighbors`, `callers`, `callees`, `impact`, `map` and `history` on that repo, `search` scoped to it (or applying the head to that repo among several), and later `path`, `deps`, `dependents` and `owners`. The caller must have the base repo in view, and the visibility check comes first: a hidden repo and a repo without that CR return the same not-found error, and only then are the `head_unavailable` reasons in the table given. Cross-repo hops read other repos' current revisions at the same publish sequence. Responses state the head sha.

Memory Verbs ignore heads. `remember` anchors only to nodes of the default-branch revision, whatever their kind (Symbol, File, Repo, Doc Section), and refuses a head anchor with a typed error; ADR 0007's anchor model is unchanged. The Concept doc gains a short "reviewing a CR" method that starts from `impact` on the head.

## Considered options

- **A change summary per head, with no queryable head graph.** Cheapest, but an agent reviewing a CR could not ask what the CR's new code calls.
- **The precise pass on same-repo heads.** Precise impact for changed code, at a fifth of the fleet budget every day, and build code run for everyone with write access.
- **A delta Shard over the base revision.** ADR 0012 rejected read-time layer merging.
- **Opt-in per repo, or skipping drafts and forks.** Most repos would never get the report, and fork CRs are the outside contributions whose impact maintainers least expect.
- **A GitHub check run with line annotations instead of the comment.** Two report shapes, and whether a check run's output can be fully withdrawn on narrowing is unverified.
- **A commit status carrying impact counts.** Statuses cannot be deleted and their history stays listable, so a count that included a since-hidden repo would stay readable forever.
- **Merge gating on impact rules.** A gate can only see the narrow ceiling, so it would ignore exactly the Restricted impact that matters.
- **Counts and a link only, or @-mentioning owners.** The first gives outside readers nothing; the second pings irrevocably on every push.
- **Diffing head against the current default branch.** Changes merged since the CR branched would show as reverted by the CR.
- **Computing impact against the revisions current when the CR branched.** Those revisions are deleted after the retention window.
- **The reporter as an Admin-issued Service Agent.** Reporting on a Restricted repo's own CR would need a Team grant, a widening, for every Restricted repo.
- **Pending Memory anchors on head Symbols, activated on merge.** Review-time Memories, at the cost of a new anchor state, merge-time mapping and orphan handling, redesigning ADR 0007's anchors.

## Consequences

- The PRD drops CR heads from its non-goals and from post-v1, amends G3, and narrows "Forges keep their jobs": Yggdrasil writes one comment per CR, and on GitHub one advisory status, and still does no code review, hosting, CI or gating.
- The report depends on M1 (`impact`, `callers`, stable Symbol IDs, fingerprints, the interface hash, `TESTS` and `EXPORTS` edges), on owners and CODEOWNERS (M2), on the web GUI for the full report, and on the GitLab and Codeberg adapters for those Forges. Where it lands is part of milestone resequencing.
- Cost, as estimates until ADR 0012's per-stage metrics measure them: one head build per CR push, at the profile's median of 61 ms per kLOC end to end, about 3 worker-hours a day at 1,000 pushes of median-sized repos; at most 50 live head pointers per repo (plus 10 short-lived GUI rebuilds), with retained storage of the live heads plus the incarnations retired within the retention window, so it grows with the push rate; one facts-only merge-base build per push and per merge-base move; drift recomputes bounded by the cached-result rule; one notice pass per head sha.
