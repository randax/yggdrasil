# Tuned SQLite Shards with loose segments, complete revisions and a symbol-level cross-repo index

Status: accepted. Refines [ADR 0005](0005-object-storage-native-shards.md): Shards stay immutable per-repo artifacts on object storage behind a Postgres control plane, and this ADR fixes what a Shard holds, how it is published and fetched, how a revision is built cheaply, and where cross-repo references live. Supplies the storage that [ADR 0011](0011-aggregated-budgeted-decisive-payloads.md) asks for, and amends [ADR 0006](0006-syntactic-ambiguity-spread-confidence.md) for calls through imported names.

The [Shard profile](https://github.com/randax/yggdrasil/blob/563e9b4c3b6a42e9583452055150a2154173b0c3/docs/research/shard-profile.md) found the problem is size, not traversal speed. Warm one-hop lookups take about 10 µs, but the median Shard costs 642 bytes per edge, 91–97% of `graph.sqlite` is the edges table and its four indexes, and a cold call downloads the whole graph segment at about 6.2 ms per MB on a local store, so webpack's 1.05 GB Shard took 6 s on first touch. Indexing wall time is mostly the full-history clone (810 s against 258 s of indexing for the corpus). The [storage-engine research](https://github.com/randax/yggdrasil/blob/bc0b8298369eed9d87eae3c2aa0718ea0826a34f/docs/research/graph-storage-engines.md) and the [incremental-indexing research](https://github.com/randax/yggdrasil/blob/7b32354068546788af58061a218478c7663ffb51/docs/research/incremental-indexing.md) set out the options; this ADR picks among them.

## The decisions

### The graph segment is tuned SQLite

The graph segment stays SQLite, rebuilt for size:

- node ids are integers inside the segment, and paths, names and other repeated strings are interned in one string table, so no edge row repeats a string id;
- edges live in clustered `WITHOUT ROWID` tables keyed for the two traversal orders: outbound by `(src, site, …)`, so all of one source's sites and their candidates are contiguous, and inbound by `(dst, kind, src, site)`, so each `(src, dst, kind)` group's evidence is contiguous. These are the orders ADR 0011's discovery batches resume on;
- the segment is written once with a fixed page size, vacuumed, and opened `immutable=1` with mmap.

The research measured a close variant of this layout (one clustered edge table plus one reverse index, on two Rust crates, syntactic only) at 8.6–9.3× smaller, about 55 bytes per edge, and about 2× faster warm lookups than the M0 schema. The layout here differs (both orders carry the site, and precise evidence is added), so that figure is a planning estimate, re-measured by the M1 schema bump's eval run. Public node ids are unchanged: the integer ids never leave the segment.

### Every candidate at an ambiguous call site is stored

94% of syntactic CALLS edges sit at call sites with several same-named candidates. The Shard stores every candidate, because ADR 0011 never hides an inbound caller and `impact` must not silently lose a caller that ranked seventh. In the outbound order a call site is one row holding its candidate list; the inbound order necessarily has one entry per candidate. Confidence is not stored per candidate: it is ADR 0006's 0.9/N, derived at read time. Locality only ranks candidates (ADR 0011); it never changes confidence.

A call site's identity is the position of the callee's name token (`Reset` in `util.Reset()`), the same in both passes. Precise evidence replaces syntactic evidence per call site, never per root: in a file its root owns and its build indexed, a site where the precise output resolves the callee token, for the same edge kind, keeps its precise evidence and drops the syntactic candidates declared in files the build indexed. Candidates declared in files the build never indexed (`opts_windows.go` when the sandbox built for Linux) stay at syntactic Provenance, with N computed over the survivors. A site the precise output did not resolve keeps its syntactic candidates, and files the build never indexed (feature-gated code, files outside the build's configuration, generated code) keep all their syntactic evidence. So a site "seen by both passes" in ADR 0011 collapses to its precise observation in the Shard, and nothing SCIP did not examine loses a caller.

### Edges to other repos are resolved per view at read time

A Shard never resolves an edge into another repo. A call into another repo is stored as external evidence keyed by an **import binding**: the ecosystem, the provider-facing import specifier (a Go import path, a Python module, an npm package name plus any subpath, a Rust crate name), and the imported name path. The specifier is canonicalised through the referencing root's own alias tables (a Cargo `package =` rename, an npm `npm:` alias, `tsconfig` `paths`, an import map), so `util::reset()` under `util = { package = "acme-util" }` is keyed by `acme_util`. The syntactic pass records a binding for every call through a name bound by an import of something the repo does not declare (`util.Reset()` where `util` imports another module, or `F()` after `import {F} from 'pkg'`). The precise pass, at the sites it resolves, records the compiler-resolved target as a version-free SCIP moniker alongside the binding. A reference only the precise pass can see (a method on an external type, whose receiver type is invisible syntactically) has a moniker and no binding. Nothing is invented: the binding is written in the source and the root's manifests, and a moniker comes from a compiler.

Each repo's revision publishes the bindings it exports: the specifiers it answers to (Go package paths, Python top-level modules, an npm package's name and export map, a crate's name) and, for each exported name path including aliases and re-exports, what it denotes: a Symbol in the repo, or, for a re-export of something imported from another repo (`export { retry } from '@acme/core'`, `pub use other::Thing`), that other binding. Exports are extracted syntactically, so they exist whether or not the providing root is precise. Monikers are published only for Symbols in precise roots.

At read time a site's target is resolved within the caller's effective view. If the site has a moniker and exactly one visible Symbol exports it, the target is that Symbol, at precise Provenance. If several visible Symbols export it (a fork or a vendored copy), each is a candidate at syntactic Provenance with ADR 0006's 0.9/N over the visible candidates. If none does, the site's binding, when it has one, is resolved through the visible exports, following re-exports from repo to repo (each hop within the view, at most a few hops, cycles cut), and every Symbol it reaches is a candidate at syntactic Provenance with ADR 0006's 0.9/N over the visible candidates: the compiler's proof covered the package it saw, not a fork or a name-path match. If nothing resolves, because the provider is hidden or was never admitted, the edge is dropped, the same way in both cases ([ADR 0008](0008-team-granted-repository-visibility.md)). Counts computed inside a Shard (degrees, `sites: n`, `+N`, hub decisions, work caps) cover only edges inside the repo, which are visible exactly when the repo is. External edges are counted only once resolved into the view.

This amends ADR 0006's rule that external names yield no edge: they still yield no invented target, but a call through an imported name is kept as external evidence.

### One copy of source text, in a contents segment

Each Shard has a contents segment: every file the indexer parsed (files of a language it extracts, plus markdown), zstd-compressed, with a line-offset table. Binary files, files over the indexer's size cap and files the repo's index rules exclude are not stored. It is the only copy of repository source text in a Shard. ADR 0011's declaration lines and call-site lines, Symbol bodies and file `search` snippets are sliced from it by file and span, and a Verb returns only spans tied to the nodes, edges or hits it returns. Tantivy indexes file bodies but no longer stores them; it still stores the text of documents that are not files (commit messages, and Forge Artifacts if they live in the Shard), so their snippets render from the revision that matched.

A trigram segment (Zoekt-style) has a reserved place in the layout. It is built only when regex search ships after v1, and then regex and diff-content search become a `search` mode without another layout decision.

### The vectors segment is separate

When semantic search lands, each Shard gains a `vectors` segment: one vector per Symbol and per Doc Section, built from text in the contents segment, quantized to int8, with a memory-mapped ANN graph. The embedding model and its version are recorded in the manifest, so changing the model rebuilds only this segment. The graph segment never holds vectors. The ANN library and the embedding model stay open (RFC 0001 §11).

### A Shard is a manifest plus loose segment files

A Shard revision is `manifest.json` plus each segment's files as separate objects: the graph segment, tantivy's files (merged to one segment at build), the contents segment and, later, the vectors and trigram segments. The manifest lists each file with its size and sha256, the state of each Precise Root (precise, with the artifact it used, or syntactic), every content-affecting input (extractor and grammar versions, the repo's index rules, the embedding model), and the commit. There is no archive.

A query node's cache stores files by sha256 and links them into a revision's directory, so a file unchanged between revisions (the contents segment when only a precise result landed) is downloaded once. Each Verb fetches only the files it needs: `node`, `neighbors` and the other graph Verbs need the graph and contents segments, `search` needs the full-text and contents segments, and semantic search needs the vectors segment.

### Publishing a revision: one publisher per repo, pre-warmed, then one atomic swap

- **Revision ids.** A revision id is the commit, the schema version and a digest of the canonical manifest. Any change to content (a new extractor, changed index rules, a landed precise result, added vectors) gives a new id, and the same content always gives the same id, so republishing is idempotent and RFC 0001 §11's schema-outdated check still finds revisions by their schema suffix. One commit can therefore have several revisions. Each upload of a revision goes to its own object prefix (the revision id plus an upload incarnation), recorded in the `shards` row, so a revision republished after GC retired it never shares objects with the incarnation being deleted.
- **One publisher per repo.** Publication holds a per-repo lease. Sync records each repo's desired head with a generation number, bumped on every head change, a reset included. A swap is a compare-and-swap on the base revision and the desired-head generation, and it refuses a revision whose schema version or indexing-policy generation (extractor and grammar versions, index rules) is older than the current one's, so neither a delayed job for an older head nor an old worker during a rolling upgrade can publish over a newer revision. The newest head wins: pending compose jobs for an older head are cancelled, and precise results landing close together are coalesced into one compose. A publisher that loses the swap only because the artifact set changed recomposes the graph segment without re-extracting.
- **Pre-warm before the swap.** The publisher records the revision as pending in Postgres, with a lease expiry, before its first upload; uploads every file; and waits until the query nodes that hold the repo acknowledge they have the changed files, or a bounded time (about a minute) passes. Then it swaps.
- **One atomic swap.** The pointer, the repo's cross-repo and package rows (below) and RFC 0001 §5.1's Memory staleness checks commit in one Postgres transaction, which also takes the next value of a global publish sequence. Pointers and rows carry the sequence range in which they were current. Every request reads at one publish sequence and opens exactly the revisions current at it, fetching cold if a node is not warm. No node serves an older revision because it has not switched yet.
- **Cold path.** A cold fetch downloads each needed file whole, as parallel byte-range GETs (the `object_store` crate coalesces and parallelises ranges), and checks its sha256. With the tuned layout the worst repo in the profile would drop from about 6 s to under 1 s on the same local store. That is derived, not measured, and real object storage is slower.
- **Escape hatch.** The fixed page size and contiguous interior pages keep a remote VFS with a hotcache of interior pages (Quickwit-style) possible without a format change. It is built if the M3 certification run shows a p95 cold fetch above 2 s for the files any graph Verb needs, for any repo.
- **Retention and GC.** A superseded revision's objects, and its rows, are kept for at least the cursor lifetime (an hour, ADR 0011) plus the longest request time. GC deletes one upload incarnation at a time, through its Postgres row marked as deleting first, and only when it is neither current nor pending and was last retired more than the retention ago. A pending incarnation whose lease expires (a lost compare-and-swap, a crashed publisher) is retired and collected the same way. Cursors issued under an older schema expire at a schema cutover with ADR 0011's expired-cursor error, because the new reader refuses old-schema Shards.

### Every revision is a complete Shard; indexing gets cheaper upstream of it

No delta or overlay Shards. Each published revision is complete, so every Verb reads one revision and the clustered contiguity, discovery-batch resume and view-computed counts above hold without merging layers. Indexing gets cheaper before publication instead:

- **Per-stage worker metrics.** Clone and fetch, archive, history, parse, resolve, segment build, upload, pre-warm and publish are timed for every job. They decide when the follow-up below is worth building.
- **A persistent mirror per worker.** Each worker keeps a bare, blobless partial clone of each repo it has indexed and fetches incrementally. History extraction reads only commits and trees (`git log --name-only`), so it needs no blobs; the syntactic pass fetches the current tree's blobs on demand. Routing a repo's jobs to the worker holding its mirror is an optimisation, never a correctness requirement.
- **Incremental history.** A job walks `git log <previous>..<new>` and merges the result with the previous revision's history facts. The facts kept for merging are every commit's touched paths, unfiltered, stored as a per-repo object keyed by head commit that is never served and is kept while a current revision was built from it; projection onto the current tree happens when the revision is composed, so a path deleted and later restored keeps its older history, and any worker can merge without a full walk. A force-push or any rewrite that removes the previous commit from the branch's ancestry falls back to a full walk.
- **A per-blob extraction cache.** Per-file facts are cached by git blob id, language, and extractor, grammar and schema versions. Cached facts are path-independent: path-derived ids are materialised after lookup, so the same blob at a new path is reused correctly. A miss only costs a parse, so the cache can live on the worker.

Resolution, segment build and upload stay proportional to the repo, which the tuned layout keeps small. Incremental resolution by name (persist each file's declaration hash and re-resolve only call sites whose candidate set changed, since ADR 0006's confidence depends on the repo-wide candidate count) is a named follow-up, built when the metrics show resolve taking a large share of the syntactic freshness target on real repos, and gated by a property test that an incremental build equals a full one.

### The precise pass builds per Precise Root and reuses unchanged results

A repo has one Shard. Inside it, Precise Roots are the units each ecosystem builds: a Cargo workspace (or a crate outside any workspace), an npm, pnpm or yarn workspace member (or a package outside any workspace), a Go module, a Python project. The precise-pass work states the rule per ecosystem. A file belongs to the root whose build owns it, and a nested root owns its subtree. Manifests under test-data and fixture paths, vendored code, and paths the repo's index rules exclude define no root. Files under no root stay syntactic. An Admin can exclude a root that cannot build, so it does not hold the repo's precision summary down.

A root's input hash covers:

- its own files, manifest and lockfile;
- every workspace-level file its ecosystem's build reads, such as a shared lockfile, `go.work`, workspace manifests, `.cargo/config.toml` or `tsconfig` bases (named per ecosystem; where an ecosystem's input closure is not known, the hash covers the whole repo tree);
- the sandbox image digest and the indexer and its version;
- the input hashes of the in-repo roots it depends on. Roots that depend on each other in a cycle are hashed together as one unit.

A precise build's raw SCIP output is stored in object storage by its own digest, which the manifest records; the root's input hash is how eligible outputs are found, so two builds of the same inputs never overwrite each other. It records the resolved dependency closure, and the hash of every file outside the root that the build indexed or that its evidence points into. Precise evidence is derived from the stored SCIP output for the current schema and ingest version, so a schema bump re-derives evidence without re-running sandbox builds. A revision uses a root's stored output when it matches the root's current input hash and the recorded outside-file hashes. A root without a committed lockfile has no reproducible dependency closure, so its output is reused for at most a day: the manifest records the expiry, a refresh build is scheduled independently of pushes, and at the deadline, if no fresh output has landed, a compose job publishes a revision with that root syntactic. Otherwise the root shows its syntactic evidence.

A root is queued for a precise build whenever the current revision has no matching output for it and no build is in flight. A build that fails for infrastructure reasons (timeout, egress failure, out of memory, a lost worker) is retried with backoff until it succeeds. A build that fails deterministically is retried daily, and an Admin can retry it at once; it stays visible per root in admin status. When an output lands, a compose job builds a new revision of the repo's desired head, picking up every matching output, and publishes it as above.

A dependency root's change changes its dependents' hashes, so a frequently changed core library leaves its in-repo dependents syntactic too until their builds land. That transitive cost is accepted, visible per root, and is the reason no stale precise edge is ever served. Every edge carries its Provenance, so an answer always shows which parts are precise. `shards.provenance_level` records the weakest level across the repo's roots not excluded by an Admin, for admin status and the precise-coverage metric; the manifest holds the per-root state.

Build caching (shared registry caches, sccache or Nix) stays an open question for the precise-pass work (RFC 0001 §11).

### Cross-repo references are a symbol-level index in Postgres

Two kinds of row, both stamped with the revision that wrote them:

- **Exports:** for each binding or moniker a revision exports, the providing repo and what it denotes: a Symbol in the repo, or a forwarded binding for a re-export.
- **References:** for each binding or moniker a revision references, per kind: the referencing repo and three counts of distinct referencing Symbols (with any site, with a precise site, with a syntactic site). Distinct referencing Symbols are the number of ADR 0011 aggregated `(src, dst, kind)` edges, the unit ADR 0011 counts degrees in.

Rows are written for every external target except language standard libraries and builtins, whether or not any admitted repo provides it yet, so admitting a provider needs no backfill and nothing about a hidden provider changes which rows exist. A revision's rows commit in the same transaction as its pointer swap, and superseded rows are kept as long as their revision's objects.

`callers(X)` and `impact` across repos start from X's own exported keys (its bindings, aliases and re-exports, and its moniker if it has one), follow forwarded-binding export rows in reverse to the keys of visible repos that re-export X (with the same hop bound and cycle cut as outbound resolution, so a hidden re-exporter never bridges two visible repos), find reference rows for all those keys from referencing repos in the caller's effective view, and open only those repos' Shards. When more than one repo in the view exports the same binding or moniker (a fork or a vendored copy), or a binding matches several visible Symbols, each is a candidate, spread like an ADR 0006 candidate set with the denominator computed on the view, so a hidden provider changes nothing. No cross-repo confidence is stored; it is derived at read time. The counts in the reference rows are routing estimates and an upper bound, used to plan work: one referencing Symbol can reach X through several keys (an alias, a subpath export, a moniker), and a syntactic match may fall below the request's confidence threshold once candidates are spread. Every degree, ranking, hub, `+N` and pagination decision instead uses the distinct referencing Symbols that survive the request's filters, read from the referencing repos' Shards, which `callers(X)` opens anyway. Package routing (`repo_packages`, `xrepo_edges`) stays and serves `deps` and `dependents`; its rows are written in the same swap and carry the same sequence ranges.

Every cross-repo request, and every page of a cross-repo cursor, reads at one publish sequence: the first page stores it in the cursor, and later pages read Shards, export, reference and package rows as of that sequence (rechecking the view as ADR 0011 requires). Hops two and beyond, re-export chains and candidate denominators therefore see the same state as the first page, and a republish between pages neither skips nor repeats a result. A cached cross-repo result records the revisions it read and the keys it looked up, including those that found nothing, and is reused only while all of them are unchanged at the request's sequence (ADR 0008's view fingerprint still applies).

A referencing root without precise coverage keeps its cross-repo callers made through imported names, at syntactic Provenance, and a providing root without precise coverage still answers for its bindings. Only moniker-keyed references (methods on external types) need both ends precise. That residue is ADR 0002's standing trade, stated here so the routing is not mistaken for a guarantee. A Tier 1 check asserts that a cross-repo caller set reached through bindings does not shrink when either end's root goes syntactic.

## Considered options

- **A custom CSR file for the graph segment.** About 23 bytes per edge, 2.4× smaller again and memory-mappable, but a custom format, writer and reader, and per-Verb query code with no SQL to fall back on. Revisit only if tuned SQLite proves too large; the Verb layer hides the change.
- **Another engine** (LadybugDB, DuckDB with DuckPGQ, Lance or Vortex). Kùzu is archived and its forks are young, DuckPGQ is research-grade, and Lance pulls in DataFusion. None beats tuned SQLite on small segments and point lookups.
- **Page-level remote reads now, or only above a size threshold.** Cold first calls become a few roundtrips instead of a download, but traversals over many leaf pages chain roundtrips, integrity needs a hash per block, and the VFS needs unsafe FFI we would own. Kept as the escape hatch above.
- **Line text inline in the graph segment, tantivy keeps bodies.** Text in two places, and regex later needs a format change.
- **Building the trigram index now.** It would cost 2–3× the source size before regex exists.
- **Delta or overlay Shards (Zoekt-style), with or without ownership sets (Glean-style).** Publication proportional to the change, but every Verb merges layers and filters tombstones, which breaks clustered contiguity, exact batch resume and per-view counts, and GC must pin bases.
- **Serving the nearest precise revision with diff-translated positions (Sourcegraph-style).** Fewer precise builds, but read-path diffing and answers that mix revisions, with fingerprints checked against one revision and precise edges from another.
- **A whole-repo precise build on every change.** Simplest, but large monorepos lose precision on every push for the length of the build.
- **Replacing a root's syntactic evidence wholesale when its build succeeds.** Simpler, but callers in files or sites the build never examined would vanish.
- **Keying cross-repo references by SCIP moniker alone.** A provider root that goes syntactic after every push has no monikers, so every precise caller of a busy library would vanish until its build lands, and moniker descriptors differ between a provider's sources and a consumer's view of them.
- **No syntactic cross-repo evidence.** Simpler, but a referencing repo with a broken build, or a root waiting for its build after every push, would drop out of `callers` and `impact`.
- **Package routing with name matching at read time for repos without precise coverage.** No storage cost, but a grep on the request path across potentially thousands of Shards.
- **Package-level cross-repo routing only.** A `callers` on a popular internal library opens every Shard that depends on its package, even when few call the Symbol.
- **Writing reference rows only for packages an admitted repo provides.** Fewer rows, but admitting a provider needs a backfill that races with publication, and a hidden provider's existence changes which rows exist.
- **A global immutable symbol segment on object storage.** Fast lookups, but rebuilt or layered on every publish, which brings back the staleness and compaction rejected for overlays.
- **Capping stored candidates per site, or dropping candidates above a candidate-count threshold.** Two to three times smaller, but inbound callers vanish, concentrated on the commonest names, and `impact` misses real callers where no precise pass runs.
- **sqlite-vec inside the graph segment.** Every cold graph fetch would also download the vectors, and a model change would rewrite the graph file.
- **A global ANN index across repos.** It breaks per-repo scoring before the merge, and every publish updates a shared index.
- **Each node switching to a new revision when its own pre-warm finishes.** Nodes and Postgres would disagree about the current revision, pairing new cross-repo rows and Memory checks with old Shards.

## Consequences

- The M1 schema bump ([RFC 0001](../rfc/0001-yggdrasil-v1.md) §11, "Shard schema evolution") carries the tuned graph segment, the contents segment, loose-file packaging, import bindings and per-root precise outputs, so the fleet re-indexes once for all of them, together with stable Symbol IDs. Later schema bumps re-derive precise evidence from stored SCIP output instead of re-running builds.
- A precise result landing publishes a new revision of the same commit. Cursors bind revisions, not commits, so they are unaffected.
- A repo whose Precise Root (or a root it depends on) changes faster than its build completes stays syntactic for that root. That is visible per root in admin status and in edge Provenance, and is accepted.
- Postgres holds every repo's external references and exports for the current revisions plus the retention window. That is a few thousand rows per repo for third-party and internal targets, written once per publish.
