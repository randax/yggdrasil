# Yggdrasil is the code-anchored team brain

The products sold as "team brains" — shared knowledge layers that people and agents query — fall into three families ([research note](../research/team-brain-landscape.md)): answer engines that embed what a company writes and synthesise cited answers (Glean, Unblocked, Atlassian Rovo, Onyx); memory engines that extract facts from agent conversations (Zep/Graphiti, mem0); and code-structure tools (Sourcegraph, Graphify). None joins precise code structure with team knowledge: the answer engines document no call graph; Sourcegraph has no write path and no non-code sources; Graphify Cloud's Memory sits on a syntactic graph with undocumented staleness behaviour; GitHub Copilot Memory re-checks code citations but has no graph and is GitHub-only SaaS. Yggdrasil takes that seam. It is the team brain *for code*: the precise, cross-repo Knowledge Graph stays the spine, and team knowledge enters only by attaching to it. We do not widen into a company-wide answer engine.

Team knowledge enters through two doors. Derived knowledge — Change Requests, issues, reviews, Doc Sections, ownership, Contributors — is already the M2 graph layer (PRD G6–G8) and keeps its `extracted`/`inferred` provenance. Asserted knowledge — what a Member (human or agent) learned that the sources do not say — enters as **Memories** (CONTEXT.md): control-plane records joined by **Anchors** to the graph nodes they concern, carrying `asserted` trust, the lowest level. Memories are the write path the graph has lacked, and the research found the combination in no surveyed product: knowledge pinned to a precise code graph that becomes detectably stale when the code it describes changes. (Copilot Memory's per-use citation re-check is the nearest mechanism; Graphify Cloud's Memory internals are undocumented.)

The decisions that make Memories trustworthy. Their mechanics are specified in RFC 0001 §5.1.

- **Memories live in the control plane, not in Shards.** Shards are immutable and rebuildable from git and the Forges (ADR 0005); Memories are written by Members and change state (promotion, staleness, retraction), and they are the only *knowledge* Yggdrasil cannot rebuild, so they belong in Postgres beside the other system-of-record state. `asserted` is a control-plane trust level, never a value of the Shard `Provenance` enum.
- **Staleness follows the code, not the clock.** An Anchor captures a content fingerprint of its node when written. When a newly published Shard revision changes that fingerprint or removes the node, the Memory is flagged stale — in the same transaction as the Shard pointer swap, never silently deleted — until a Member affirms, supersedes or retracts it. This needs two graph-side guarantees: a per-node fingerprint in the Shard, and Symbol identity that is stable across the syntactic and precise passes and across package versions. Those land with the M1 precise pass, which is why Memories follow M1. Semantic Memory is never expired by time; Episodic Memory is bound to a client session and expires.
- **Derived and asserted knowledge never blur.** Derived Verbs (`search`, `node`, `neighbors`, `callers`, …) never return Memories. Memories are read only through `recall`, which returns each one with its author, scope, staleness and `asserted` trust, and returns bodies as untrusted data. A Memory is a claim to check against the graph, never an instruction: the shipped Skill says so, and an eval with a promoted, injected instruction tests it.
- **Private until promoted, and only while the code is admitted.** *Scope* (session → repo → org) decides where a Memory is recalled; *sharing* decides who sees it. A new Memory lands in its author's private overlay. **Promotion** into the shared pool is an explicit, audited act, and only Members granted the promote right may complete it (by default human Members, not agents). An agent's `promote` becomes a proposal to a named reviewer who accepts or rejects exactly what was proposed (Memories are immutable; a change is a new, superseding Memory), so by default agent-written knowledge reaches the team through a human gate. An Admin may grant an agent the right explicitly, and that grant is audited. The gate depends on credential separation: agents, including those behind `yg mcp`, act under their own agent Member tokens, never a human's. The same right is needed to affirm a stale shared Memory back into trust. Once shared, a Memory follows ADR 0001 and is visible to every Member. But it is recallable only while every repo it anchors to is still indexed: excluding a repo hides its Memories, so un-indexing still keeps a sensitive repo private. A Memory must anchor every repo whose non-public content it discloses, and promoting it attests the content is fit for org-wide view. Writes a secret scanner flags are rejected. Retraction suppresses a Memory everywhere at once, and Admins can erase bodies outright. Both go to an append-only object-storage log (object-locked where the store supports it) that is excluded from restores and replayed before reads resume.
- **Writing needs identity.** Memories are attributed, authorised and quota'd per Member, so the Memory slice ships Admin-issued Member tokens (RFC 0001 §2) if they have not already landed. It cannot run on the bootstrap Admin token.
- **The Verb set grows; it does not open up.** Memory adds four bounded Verbs — `remember` (create, supersede or affirm), `recall`, `promote` and `retract` — identical across CLI, MCP and HTTP. This extends ADR 0003's curated set rather than reversing it: there is still no query language, the change is additive within the contract version, and the Skill's contract version bumps with it.

Sequencing changes with this decision. The Memory slice opens M2: after the M1 precise core and before the rest of M2's layers, so Forge Artifacts arrive in a graph that can already hold "why" knowledge and cite it. Semantic retrieval stays at M3 by PRD G10's explicit decision. Most answer and memory products already have it, so it is table stakes rather than separation — and Graphify, the nearest competitor, has none in its open engine. Until M3 we accept weaker fuzzy recall.

What Yggdrasil deliberately leaves to others: ingesting chat, ticket systems outside the Forges and documents outside indexed repos; synthesising natural-language answers; and a chat or wiki front end. Answer engines do this well, and doing it would need an LLM on the query path, permission mirroring and content egress, against ADR 0001 and the no-egress default. Instead Yggdrasil is the code back end that agents call over MCP, as can answer engines that accept custom MCP sources (Unblocked does today). The agent composes the answer; Yggdrasil supplies trusted structure and anchored memory. The cost is stated plainly: by the research note's own measure, without chat and ticket sources Yggdrasil is a team brain for code, not a complete team brain.

Rejected:
- **Becoming a company-wide answer engine.** That is a breadth race against Glean and Unblocked, and the structural graph becomes one source among many.
- **Bolting an external memory engine such as mem0 or Zep beside the graph.** That means two stores, no Anchors and no code-driven staleness.
- **Storing Memories in Shards.** It breaks immutability, and knowledge would depend on a rebuild.
- **Time-based expiry for Semantic Memory,** as in GitHub Copilot Memory's 90-day default. It expires knowledge that is still true. Copilot offsets this with a per-use citation re-check; Anchors generalise that re-check to graph nodes.
- **Making Memories org-visible on write.** One careless agent would publish a credential or a wrong claim to every Member.
- **Scheduling Memory after M3 semantic search.** That cedes the uncrowded position to Graphify Cloud, which shipped `remember`/`recall` in October 2026 on a syntactic graph, and to Copilot Memory.
