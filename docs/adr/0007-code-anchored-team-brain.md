# Yggdrasil is the code-anchored team brain

The market for "team brains" — shared knowledge layers that people and agents query — splits three ways ([research note](../research/team-brain-landscape.md)): answer engines that embed everything a company writes and synthesise cited answers (Glean, Unblocked, Atlassian Rovo, Onyx); memory engines that extract facts from agent conversations (Zep/Graphiti, mem0); and code-structure tools that know how code connects but little else (Sourcegraph, Graphify). None joins the two halves: answer engines cannot enumerate call sites, and code tools cannot say why the code is the way it is or what a teammate's agent learned about it yesterday. Yggdrasil takes that seam. It is the team brain *for code*: the precise, cross-repo Knowledge Graph stays the spine, and team knowledge enters only by attaching to it. We do not widen into a company-wide answer engine.

Team knowledge enters through two doors. Derived knowledge — Change Requests, issues, reviews, Doc Sections, ownership, Contributors — is already the M2 graph layer (PRD G6–G8) and keeps its `extracted`/`inferred` provenance. Asserted knowledge — what an agent or engineer learned that the sources do not say — enters as **Memories** (CONTEXT.md): Memory nodes with an **Anchor** edge to the Symbol, file or other node they concern, carrying `asserted` provenance, the lowest trust level. Memories are the write path the graph has lacked and the one capability in this design that no surveyed product has: knowledge pinned to a precise code graph that becomes detectably stale when the code it describes changes.

The decisions that make that trustworthy:

- **Memories live in the control plane, not in Shards.** Shards are immutable and rebuildable from git and the Forges (ADR 0005); Memories are mutable and are the first knowledge Yggdrasil cannot rebuild, so they belong in Postgres beside the other system-of-record state. Postgres backups now protect knowledge, not only configuration — the deployment docs must say so.
- **Staleness follows the code, not the clock.** When a newly published Shard revision changes or removes an anchored node, the Memory is marked stale — never silently deleted — and returned with that flag until someone reaffirms, supersedes or retracts it. Semantic Memory is never expired by time; Episodic Memory (session state) expires. Anchors key on stable symbol identity, which is precise only once the M1 pass exists; that is why Memories follow M1. A Memory anchored to a syntactic-only node may be marked stale more readily than one anchored to a precise node, and the stale reason says which.
- **Derived and asserted knowledge never blur.** Derived Verbs (`search`, `node`, `neighbors`, `callers`, …) return only derived graph content. Memories are read through their own Verb and always carry `asserted` provenance plus author, creation time and staleness, so an agent can never mistake a claim for an extracted fact.
- **Private until promoted.** Two things are kept apart: *scope* (session → repo → org, CONTEXT.md) decides where a Memory is recalled, and *sharing* decides who sees it. A new Memory lands in its author's private overlay, visible only to that Member. **Promotion** is the explicit, attributed act that moves it into the shared pool and may widen its scope. Once shared, it follows ADR 0001: visible to every Member, like everything else the Index Server holds. Episodic Memory stays private and session-scoped. Memories inherit their anchor repo's admission — a Memory cannot anchor to a repo that is not indexed. Writes are rejected when a secret scanner flags the body. This bounds the leak risk that org-visibility creates for free-text knowledge, without reopening ADR 0001 for the derived graph.
- **Writing needs identity.** Memories are attributed to a Member, so the Memory slice depends on Admin-issued Member tokens (RFC 0001 §2) and cannot ship on the bootstrap Admin token alone.
- **The Verb set grows, it does not open up.** Memory adds three bounded Verbs — `remember` (create or supersede), `recall` (by anchor, by scope, or by full-text query) and `promote` — identical across CLI, MCP and HTTP, extending ADR 0003 rather than reversing it. Their parameters are specified in RFC 0001 §7 before implementation begins.

Sequencing changes with this decision. The Memory slice opens M2, after the M1 precise core and before the rest of M2's layers, so that Forge Artifacts arrive into a graph that can already hold "why" knowledge and cite it. Semantic retrieval stays at M3: every competitor has it, so it differentiates nothing, whereas precise edges plus anchored Memories do.

What Yggdrasil deliberately leaves to others: ingesting chat, tickets outside the Forges, and company documents; synthesising natural-language answers; and a chat or wiki front end. Answer engines do this well, and doing it would need an LLM on the query path, permission mirroring and content egress, against ADR 0001 and the no-egress default. Instead, Yggdrasil is the code back end those tools and agents call over MCP: the agent composes the answer, and Yggdrasil supplies trusted structure and anchored memory.

Rejected: becoming a company-wide answer engine (the breadth race against Glean and Unblocked, with the structural graph reduced to one source among many); bolting an external memory engine such as mem0 or Zep beside the graph (two stores, no Anchors, no code-driven staleness); storing Memories in Shards (breaks immutability and makes knowledge depend on a rebuild); time-based expiry for Semantic Memory as in GitHub Copilot Memory's 90-day default (expires knowledge that is still true and keeps knowledge the code has already invalidated); org-visible by default on write (one careless agent publishes a credential or a wrong claim to every Member); and scheduling Memory after M3 semantic search (cedes the only uncrowded position to Graphify Cloud, which shipped `remember`/`recall` in October 2026 on a syntactic graph, and to Copilot Memory).
