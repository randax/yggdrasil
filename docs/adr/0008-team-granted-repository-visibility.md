# Repository visibility is granted per Team

Status: accepted. Supersedes the access model of ADR 0001; ADR 0001's discovery and admission rules still stand.

ADR 0001 made everything indexed visible to every Member and kept sensitive repos private by not indexing them. Teams (CONTEXT.md) end that: an Organization that wants one brain over all its code cannot also leave its private repos out of it. So **Visibility** is now decided per Member, from the Teams they belong to. Admission still decides *what is indexed*; Visibility decides *who may see it*. A repo must be both admitted and visible before any Verb touches it.

The unit is the repository, never the path ([research note](https://github.com/randax/yggdrasil/blob/1959d84908ddb599662c79a86592f6183d2adb3c/docs/research/visibility-filtering.md), option A). Grants are control-plane rows, and a query sees a repo only by having that repo's Shard selected for it. Every Shard keeps its own tantivy segment, and its scores are normalised inside that repo before the merge (RFC 0001 §7), so a hidden repo cannot shift a visible repo's scores or ordering. A visibility change rewrites no Shard, which keeps them immutable (ADR 0005), and queries pinned to an older Shard revision follow the change at once. The cost is computing each Member's visible set and invalidating it when Teams or grants change.

## The rules

- **Open or Restricted.** An Open repo is visible to every Member. A Restricted repo is visible only to Members of the Teams granted it. When a repo is admitted, repos that are public or internal on the Forge default to Open, and repos private on the Forge default to Restricted. (The Forge's own public, internal or private setting is an input to this default, never Visibility itself.) If the Forge later makes an Open repo private, it becomes Restricted at the next sync unless an Admin override is on record. An Admin may override either default, with step-up, and the change is audited. Admission is otherwise unchanged: private repos are still discovered-but-not-indexed until an Admin opts them in (ADR 0001), so a new private repo becomes neither indexed nor visible on its own.
- **Grants come from the Forge or from an Admin.** A Team synced from a Forge team (a GitHub or Codeberg team, a GitLab group) is granted every repo that Forge team can read. An Admin may also grant a repo to any Team explicitly; that needs step-up and is audited. Team Maintainers cannot grant repos, and adding a Member is a widening too. A Team synced from a Forge team takes its membership from the Forge alone: locally, an Admin or the Team Maintainer can only remove Members, by a local revoke. A Team that is not synced can have Members added locally; when it holds Restricted grants, each addition needs step-up, is audited and notifies the Owning Teams of those repos, as an Admin's widening does. Grants only add Visibility. The one negative rule is a local revoke (below), which suppresses a Forge-derived grant or membership; there is no deny rule against a repo. Outside collaborators of a Forge repo gain nothing through these grants, because Visibility follows Teams, not per-person Forge permissions.
- **Hidden is indistinguishable from nonexistent.** A repo the caller cannot see is refused with the same error and response shape as a repo that does not exist. Visibility is checked *before* the "registered but not yet indexed" distinction, so that message cannot be used to discover a hidden repo. Graph edges, Dependencies, Change Requests and other Forge Artifacts that lead into or out of a hidden repo are dropped, never redacted or counted. A Dependency that resolves to a hidden repo is shown exactly as an unresolved external package. Every count, rank and centrality figure a Verb or status endpoint returns (repo counts, edge summaries, Map landmarks) is computed over the caller's visible set only. What the caller cannot see is reported to the people who can. When a query or report reaches impact in a hidden repo, a private notice goes to the Members of that repo's Owning Teams who can see it; when there are none, Admins get an operational alert that names only the repo. The caller is told nothing. A notice names the affected Symbols in the hidden repo. It names the caller and their source repo only to recipients who can see that source repo, and tells everyone else "a change in a repo you cannot see". Notices are deduplicated per change and per day and rate-limited per caller, so repeated queries can be used neither to spam nor to probe. The same recipient rule applies to every notice this ADR calls for: Break-glass and widening notices also go only to Owning Team Members who can see the repo, with the same Admin fallback.
- **Published artifacts serve their least-privileged reader, and the server enforces it.** An artifact that people other than the requester will read is computed for the reader who can see least, including readers outside the Organization. A Service Agent never filters for itself: each of its queries carries a reader ceiling that the server applies, and the ceiling can only narrow the agent's own view, so a prompt injected into a Change Request or a channel cannot widen an answer. The ceiling per surface:
  - **PR impact report:** when the Change Request's repo is public on the Forge, Forge-public repos only. Otherwise Open repos plus that repo.
  - **Ask in a chat channel:** Open repos when the chat workspace admits only Organization Members, and Forge-public repos only in guest or shared channels. An Admin may bind a channel to a Team; while only that Team's Members are in the channel, answers use that Team's view.
  - **Ask in a direct message:** the asking Member's own view.
  Hidden impact reaches the Owning Teams as a notice, never the shared artifact. How membership of a channel is checked belongs to the Ask agent's chat-adapter contract; how a repo's Forge visibility is read belongs to the PR impact report design.
- **Memories need their Audience and every anchored repo.** A Member recalls a Memory only when they are in its Audience *and* can see every repo it is anchored to. This replaces ADR 0007's "recallable only while every repo it anchors to is still indexed" with "visible to the caller", and narrows its "attests the content is fit for org-wide view" to fitness for the chosen Audience. Within a supersession chain, each caller gets the newest version visible to them, and a write that names a head the caller cannot see is refused exactly as if that head did not exist, so a refusal never reveals a hidden successor. A reviewer of a Proposal must be able to see every one of its anchored repos.
- **Admins see only what their Teams grant.** Running the deployment does not grant Visibility. A human Admin who must see a Restricted repo outside their Teams opens a **Break-glass Session**. The session needs step-up and a stated reason, names the repos, expires quickly, and is audited, and the repos' Owning Teams are told it happened. It belongs to the human's stepped-up session alone: their Personal Agents do not share it, and their other tokens do not gain from it. While it lasts, the named repos count as visible to that session, so the recall rule above applies to Memories anchored to them. Admins keep their operational powers over a Restricted repo, but none of them widens access silently. Every Admin act that widens who can see it needs step-up and a stated reason, is audited, and notifies the repo's Owning Teams exactly as a Break-glass Session does. Those acts are: an explicit grant, a change from Restricted to Open, a Team assignment for a Service Agent that reaches the repo, and a change to the ownership rule that routes its notices. Two-Admin approval may come later; it is not part of this decision.
- **Revocation lag is bounded and fails closed.** Forge-derived membership needs a verified binding between a Member and their Forge account (Forge login or an Admin-set binding), never the inferred Contributor identity merge. Forge-derived memberships and grants converge within one stated sync interval, sped up by Forge webhooks where offered and never dependent on them. An Admin may locally revoke any Forge-derived grant or membership, and a Team Maintainer any Forge-derived membership of their Team, with immediate effect; the local revoke overrides sync until it is explicitly cleared, by an Admin, or by the Team Maintainer who made it. A Forge-derived grant or membership that sync has not reconfirmed within a maximum age lapses until sync succeeds again, so a long Forge outage degrades to less Visibility, never to stale access. Explicit Admin grants do not lapse. The interval and maximum age will be set by the Identity and login ticket on the wayfinder map (#133) and then written into RFC 0001.
- **Cursors and caches belong to one Member's view.** A signed cursor carries the Member's id and a fingerprint of their view when it was issued: their visible set, any Break-glass Session, and, for Memory Verbs, the Audiences they belong to. Presented by another Member, or after the issuer's view has changed, it is refused with the same error as an expired cursor. Only derived Verbs share result caches, keyed by the visible-set fingerprint, so Members share an entry only when they see exactly the same repos. Memory Verbs are never cached across Members. Revocation therefore needs no extra cursor or cache invalidation.

## Considered options

- **Keep ADR 0001's org-visible model and continue not indexing sensitive repos.** That is simplest, but it rules out Teams as a boundary and leaves the most sensitive code outside the brain.
- **Per-document ACLs inside the Shard** (research option B, the Onyx and Glean pattern). Path-level rules become possible, but every visibility change rewrites Shards, against ADR 0005. Within-repo IDF would also count hidden documents unless the scorer were rewritten.
- **Repo grants plus a path post-filter** (option C, Sourcegraph sub-repo permissions). Results over-fetch and paginate in loops, and within-repo scores can leak hidden content. Every Verb would need the hook. Path- and directory-level restriction is out of scope for this effort.
- **Mirroring each person's Forge permissions** instead of granting per Team. This needs per-person sync across three Forges, and outside collaborators and per-person exceptions turn into hidden visibility nobody manages in Yggdrasil.
- **Forbidding Admins from granting a Restricted repo to their own Teams or Service Agents.** An Admin can grant it to an empty Team and then join that Team, and the rule blocks legitimate setup in deployments with one Admin. Notifying the Owning Teams of every widening closes the silent path without either cost.
- **Allowing Restricted grants only to Forge-synced Teams.** Simpler, but every restricted group must then be modelled on the Forge. Notifying on local additions keeps local Teams useful.
- **Letting the publishing agent filter its own results**, or using the requester's view with a warning not to share. The first is a confused deputy that a prompt injection can turn; the second leaks the moment an answer is posted.
- **Forge-public repos only for every published artifact.** Safe, but useless for an Organization whose code is mostly private.
- **Redacting hidden results** ("3 results hidden") instead of dropping them. A count or a placeholder still discloses that hidden code exists and roughly where.
- **Keeping last-known grants through a Forge outage.** Nothing breaks, but revocation then waits on the Forge for as long as the outage lasts.
- **Cursors that hold positions only** and re-check visibility on every page. Correct only while every page and cache path remembers to re-check. Binding them to the Member's view fails closed by construction.

## Consequences

- Every place that asks "is this repo admitted?" now asks "is it visible to this caller?": target resolution, search fan-out, graph traversal across repos, Memory recall and the review queue. One function owns that answer.
- Owning Team impact notices and Break-glass notices need a notification path; Service Agent queries need a reader-ceiling parameter that the server enforces.
- Forge sync now carries access decisions. Its freshness becomes a stated objective, and its failure mode is less Visibility.
- RFC 0001 still describes the ADR 0001 model: §5.1's "while every repo it anchors to is indexed" and "fit for org-wide visibility", §3's restore rule and §10's ADR list. They are rewritten to this ADR in the map's RFC consolidation step; until then this ADR wins where they disagree.
