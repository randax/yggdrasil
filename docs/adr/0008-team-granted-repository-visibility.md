# Repository visibility is granted per Team

Status: accepted. Supersedes the access model of ADR 0001; ADR 0001's discovery and admission rules still stand.

ADR 0001 made everything indexed visible to every Member and kept sensitive repos private by not indexing them. Teams (CONTEXT.md) end that: an Organization that wants one brain over all its code cannot also leave its private repos out of it. So **Visibility** is now decided per Member, from the Teams they belong to. Admission still decides *what is indexed*; Visibility decides *who may see it*. A repo must be both admitted and visible before any Verb touches it.

The unit is the repository, never the path ([research note](https://github.com/randax/yggdrasil/blob/research/visibility-filtering/docs/research/visibility-filtering.md), option A). Grants are control-plane rows, and a query sees a repo only by having that repo's Shard selected for it. Every Shard keeps its own tantivy segment, and its scores are normalised inside that repo before the merge (RFC 0001 §7), so a hidden repo cannot shift a visible repo's scores or ordering. A visibility change rewrites no Shard, which keeps them immutable (ADR 0005), and every pinned revision follows the change at once. The cost is computing each Member's visible set and invalidating it when Teams or grants change.

## The rules

- **Open or Restricted.** An Open repo is visible to every Member. A Restricted repo is visible only to Members of the Teams granted it. When a repo is admitted, public and internal repos default to Open and private repos default to Restricted. An Admin may override either default, with step-up, and the change is audited. Admission is otherwise unchanged: private repos are still discovered-but-not-indexed until an Admin opts them in (ADR 0001), so a new private repo becomes neither indexed nor visible on its own.
- **Grants come from the Forge or from an Admin.** A Team synced from a Forge team is granted every repo that Forge team can read. An Admin may also grant a repo to any Team explicitly; that needs step-up and is audited. Team Maintainers cannot grant repos. Grants only add visibility; there is no deny rule. Outside collaborators of a Forge repo gain nothing through these grants, because Visibility follows Teams, not per-person Forge permissions.
- **Hidden is indistinguishable from nonexistent.** A repo the caller cannot see is refused with the same error and response shape as a repo that does not exist. Visibility is checked *before* the "registered but not yet indexed" distinction, so that message cannot be used to discover a hidden repo. Graph edges, Dependencies, Change Requests and other Forge Artifacts that lead into a hidden repo are dropped, never redacted or counted. What the caller cannot see is reported to the people who can: when a query or report reaches impact in a hidden repo, that repo's Owning Team gets a private notice, and the caller is told nothing.
- **Published artifacts serve their least-privileged reader.** An artifact posted where Members other than the requester will read it — an Ask answer in a chat channel, a PR impact report on a Change Request — is computed as if for the reader who can see least: the intersection of what that audience can see, which in practice means Open repos plus the repo the artifact is about. Hidden impact reaches the Owning Team as above, never the shared artifact.
- **Memories need their Audience and every anchored repo.** A Member recalls a Memory only when they are in its Audience *and* can see every repo it is anchored to. This replaces ADR 0007's "recallable only while every repo it anchors to is still indexed" with "visible to the caller", and narrows its "attests the content is fit for org-wide view" to fitness for the chosen Audience. Within a supersession chain, each caller gets the newest version visible to them. A reviewer of a Proposal must be able to see every one of its anchored repos.
- **Admins see only what their Teams grant.** Running the deployment does not grant Visibility. A human Admin who must see a Restricted repo outside their Teams opens a **Break-glass Session**. The session needs step-up and a stated reason, names the repos, expires quickly, and is audited, and the repos' Owning Teams are told it happened. Admins keep every operational power over a Restricted repo that does not reveal its content: admitting it, changing its default, granting it to Teams.
- **Revocation lag is bounded and fails closed.** Forge-derived memberships and grants converge within one stated sync interval, sped up by Forge webhooks where offered and never dependent on them. An Admin, or the Team's Maintainer for membership, may revoke locally with immediate effect; the local revoke overrides sync until it is explicitly cleared. A Forge-derived grant or membership that sync has not reconfirmed within a maximum age lapses until sync succeeds again, so a long Forge outage degrades to less visibility, never to stale access. Explicit Admin grants do not lapse. The interval and maximum age are set by the identity-and-login design and RFC 0001.
- **Cursors and caches belong to one Member's view.** A signed cursor carries the Member's id and a fingerprint of their visible set when it was issued. Presented by another Member, or after the issuer's visible set has changed, it is refused with the same error as an expired cursor. Result caches are keyed by the visible-set fingerprint, so Members share an entry only when they see exactly the same repos. Revocation therefore needs no extra cursor or cache invalidation.

## Considered options

- **Keep ADR 0001's org-visible model and continue not indexing sensitive repos.** That is simplest, but it rules out Teams as a boundary and leaves the most sensitive code outside the brain.
- **Per-document ACLs inside the Shard** (research option B, the Onyx and Glean pattern). Path-level rules become possible, but every visibility change rewrites Shards, against ADR 0005. Within-repo IDF would also count hidden documents unless the scorer were rewritten.
- **Repo grants plus a path post-filter** (option C, Sourcegraph sub-repo permissions). Results over-fetch and paginate in loops, and within-repo scores can leak hidden content. Every Verb would need the hook. Path- and directory-level restriction is out of scope for this effort.
- **Mirroring each person's Forge permissions** instead of granting per Team. This needs per-person sync across three Forges, and outside collaborators and per-person exceptions turn into hidden visibility nobody manages in Yggdrasil.
- **Redacting hidden results** ("3 results hidden") instead of dropping them. A count or a placeholder still discloses that hidden code exists and roughly where.
- **Keeping last-known grants through a Forge outage.** Nothing breaks, but revocation then waits on the Forge for as long as the outage lasts.
- **Cursors that hold positions only** and re-check visibility on every page. Correct only while every page and cache path remembers to re-check. Binding them to the Member's view fails closed by construction.

## Consequences

- Every place that asks "is this repo admitted?" now asks "is it visible to this caller?": target resolution, search fan-out, graph traversal across repos, Memory recall and the review queue. One function owns that answer.
- Owning Team impact notices and Break-glass notices need a notification path; the PR impact report and the Ask agent need a way to compute their reader's visible set.
- Forge sync now carries access decisions. Its freshness becomes a stated objective, and its failure mode is less visibility.
