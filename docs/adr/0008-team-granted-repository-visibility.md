# Repository visibility is granted per Team

Status: accepted. Supersedes the access model of ADR 0001; ADR 0001's discovery and admission rules still stand.

ADR 0001 made everything indexed visible to every Member and kept sensitive repos private by not indexing them. Teams (CONTEXT.md) end that: an Organization that wants one brain over all its code cannot also leave its private repos out of it. So **Visibility** is now decided per Member, from the Teams they belong to. Admission still decides *what is indexed*; Visibility decides *who may see it*. A repo must be both admitted and in the caller's view before any Verb touches it.

The unit is the repository, never the path ([research note](https://github.com/randax/yggdrasil/blob/1959d84908ddb599662c79a86592f6183d2adb3c/docs/research/visibility-filtering.md), option A). Grants are control-plane rows, and a query sees a repo only by having that repo's Shard selected for it. Every Shard keeps its own tantivy segment, and its scores are normalised inside that repo before the merge (RFC 0001 §7), so a hidden repo cannot shift a visible repo's scores or ordering. A visibility change rewrites no Shard, which keeps them immutable (ADR 0005), and queries pinned to an older Shard revision follow the change at once. The cost is computing each Member's visible set and invalidating it when Teams or grants change.

## The rules

### What a Member can see

- **Visible means admitted, and Open or granted.** A Member's *view* is the set of repos they can see: every admitted Open repo, and every admitted Restricted repo granted to one of their Teams. A *Team's view* is every admitted Open repo plus the repos granted to that Team. A repo that is not admitted is in no one's view. Every place that asks "is this repo admitted?" asks "is it in this caller's view?" instead.
- **Open or Restricted.** An Open repo is visible to every Member. A Restricted repo is visible only to Members of the Teams granted it. When a repo is admitted, repos that are public or internal on the Forge default to Open, and repos private on the Forge default to Restricted. The Forge's own public, internal or private setting is an input to this default, never Visibility itself. An Admin may override either default. Whenever a repo goes from Open to Restricted, whether the Forge or an Admin made the change, explicit grants made while it was Open are suspended until an Admin confirms each one as a fresh widening. Admission is otherwise unchanged (ADR 0001): a private repo stays discovered-but-not-indexed until an Admin's rule admits it.
- **Forge changes never widen.** When the Forge makes a repo private, it becomes Restricted at once, whether or not it stays admitted, and its admission is re-evaluated under ADR 0001. That Restricted state is sticky: no rule or override written before the change reopens it, only a fresh Admin widening. When the Forge makes a Restricted repo public, it stays Restricted until an Admin changes it.
- **Grants come from the Forge or from an Admin.** A Team synced from a Forge team (a GitHub or Codeberg team, a GitLab group) is granted every repo whose code that Forge team has itself been given access to read. Access that does not include reading code is never a grant: a GitLab group invited at Guest, or a Forgejo team holding only the Issues unit, grants nothing. Only active members of the Forge team whose own role carries code-read access count as its Members; pending invitations and Guest or Minimal Access roles do not. Read access that comes only from a repo being public or internal on the Forge, or from an organization-wide base permission, is never a grant, so a Forge visibility change cannot create one. An Admin may grant a repo to any Team explicitly. Team Maintainers cannot grant repos. Grants only add Visibility; the one negative rule is a local revoke (below), which suppresses a Forge-derived grant or membership. Outside collaborators of a Forge repo gain nothing through grants, because Visibility follows Teams, not per-person Forge permissions.
- **Membership.** A Team synced from a Forge team takes its human membership from the Forge alone; locally, an Admin or the Team Maintainer can only remove Members, by a local revoke. An Admin may still assign Service Agents to any Team, synced or not, and that assignment is a widening. A Team that is not synced can have Members added locally. Forge-derived membership needs a verified binding between a Member and their Forge account (Forge login, or a binding an Admin sets), never the inferred Contributor identity merge.

### Widening access is never silent

- **Every widening needs a reason and sends a notice.** Any act by a Member that increases who can see a Restricted or Forge-private repo needs step-up and a stated reason, is audited, and sends a widening notice (below). That covers, among others: an explicit grant; a change from Restricted to Open; an admission rule or override that admits Forge-private repos as Open, which is a widening when written and sends a widening notice for each repo it later matches; adding a Member to an unsynced Team that holds Restricted grants; assigning a Service Agent to a Team that reaches the repo; linking a Team to a Forge team; setting a Member's Forge-account binding; clearing a local revoke; issuing a token for a Member other than oneself; and changing the ownership rule that routes the repo's notices, which notifies the Owning Teams from before and after the change. Widening that sync derives from the Forge (a Forge team gains a member or read access) has no acting Member: it is audited but needs no step-up and sends no notice, because the Forge is the authority for it. A repo that is un-admitted and later re-admitted returns to the narrower of the Visibility it had and its Forge-derived default (overrides ignored), never to a fresh default. Two-Admin approval may come later; it is not part of this decision.
- **Admins see only what their Teams grant.** Running the deployment does not grant Visibility. A human Admin who must see a Restricted repo outside their Teams opens a **Break-glass Session**: step-up, a stated reason, named repos, a short expiry, an audit record and a notice. The session belongs to that human's stepped-up session alone. Their Personal Agents do not share it and their other tokens gain nothing from it. While it lasts, the named repos that are still admitted are in that session's view, so the recall rule below applies to Memories anchored to them.

### What a hidden repo looks like

- **Hidden is indistinguishable from nonexistent.** A repo outside the caller's view is refused with the same error and response shape as a repo that does not exist. The view is checked *before* the "registered but not yet indexed" distinction, which is only ever reported for a repo in the caller's view. Graph edges, Change Requests and other Forge Artifacts that lead into or out of a hidden repo are dropped, never redacted or counted. A Dependency declared in a visible repo's manifest is kept, but its resolution to a hidden repo is dropped, so it is shown exactly as an unresolved external package. A node that belongs to no single repo (a Contributor, a Concept, a package) exists for a caller only when at least one of its sources is in the caller's view, and its attributes, its edges and its identity are derived from those sources alone. Two Contributor aliases are shown as one person only when the evidence that merges them is in the caller's view. Every count, rank and centrality figure a Verb or Member-facing status endpoint returns (repo counts, edge summaries, Map landmarks) is computed over the caller's view only. Admin-only operational surfaces may name Restricted repos, but never show their content.

### Notices

- **Hidden impact is reported to those who can see it.** When the `impact` Verb run on a change reaches code in a repo outside the caller's view, the caller is told nothing, and a private impact notice is sent. For a Change Request the pass runs once per change, as if the PR's author were the caller (an author who is not a Member, such as a fork contributor or a bot, counts as having the Forge-public set plus the Change Request's own repo in view, since they can already read that repo on the Forge; a Change Request with no head revision gets a diff-only pass, [ADR 0013](0013-pr-impact-report.md)), whatever the comment's ceiling and whoever later opens the full report. Opening the report in the web GUI sends no notice. Read-only Verbs such as `callers`, `neighbors` and `search` drop hidden results silently and send no notice. Hidden impact is found by a separate pass that runs as the Index Server itself over every admitted repo and feeds only the notice path. Its results are never returned to the caller, cached under the caller's view, or bound into a cursor. It names the affected Symbols in the hidden repo. It names the caller and their source repo only to recipients whose view includes that source repo. Everyone else is told "a change in a repo you cannot see". This is a deliberate, accepted disclosure: an Owning Team learns that some repo it cannot see touches its code, which is the reason the notice exists.
- **Recipients.** "The repo" is the hidden repo for an impact notice, and the repo widened or opened for a widening or Break-glass notice. The recipient tiers are:
  1. Members of the Owning Teams of the affected code (its CODEOWNERS entries, or else the Admin rule) whose view includes the repo;
  2. Team Maintainers of the Teams granted the repo, whose view includes the repo;
  3. Admins, as an operational alert that names only the repo. Admins are not filtered by view, and the alert carries no content.

  An impact notice goes to the first tier with a recipient. A widening or Break-glass notice goes to every tier. The acting Member never counts as a recipient; when no one else qualifies, the act is still audited and its notice is held for the first Member who later does. Impact notices are deduplicated per change and per day and rate-limited per caller, so repeated queries can be used neither to spam nor to probe. Widening and Break-glass notices are never deduplicated, rate-limited or dropped; they may be batched, but every act is listed.

### Published artifacts

- **Published artifacts serve their least-privileged reader, and the server enforces it.** An artifact that people other than the requester will read is computed for the reader who can see least, including readers outside the Organization. Precisely, its ceiling holds only repos and Audiences that every one of its readers may see: the intersection of their views, not any one reader's view. A Service Agent never filters for itself. Each of its queries is bound to a *reader ceiling*: a set of repos and a set of Memory Audiences. The server derives the ceiling from the surface the query is for, attested by the surface's adapter credential, never from anything the model chooses. For the web GUI that credential is presented on an internal-only listener together with the Member's own session ([ADR 0014](0014-web-gui-stack.md)). A Service Agent query without one is refused. The server intersects the agent's own view with the ceiling's repos, and the agent's own Audiences with the ceiling's Audiences; for an on-behalf-of Service Agent such as Ask, the asker's view and Audiences take the place of the agent's own ([ADR 0010](0010-ask-agent-and-chat-adapters.md)). The ceiling can only narrow the result, so a prompt injected into a Change Request or a channel cannot widen an answer. In the table, *Forge-public repos* means admitted, Open repos whose code anyone on the internet can read, as [ADR 0013](0013-pr-impact-report.md) defines it (self-managed Forges count only when an Admin attests them as world-readable); a Forge-public repo an Admin made Restricted is not in the Forge-public set. It reaches a shared surface only through a Team's view, as in a Team-bound channel. A Memory enters an artifact only when every reader of that surface could recall it themselves. On shared surfaces every repo it anchors to must therefore be Open. This anchor check uses Open repos, not the ceiling's repo set, so a Memory anchored to a Restricted repo reaches no open channel. The exceptions are a Team-bound channel, where its anchors need only be in that Team's view, and a direct message, where they need only be in the asker's view.

  | Surface | Repos | Memories |
  |---|---|---|
  | PR impact report comment on any Change Request | Forge-public repos plus that repo | none |
  | Ask in a channel whose every reader is a bound, active Member (ADR 0010) | Open repos | Organization Audience only |
  | Ask in a guest or shared channel | Forge-public repos only | none |
  | Ask in a private channel an Admin bound to a Team, while every reader is a bound, active Member of that Team | that Team's view | Organization and that Team |
  | Ask in a direct message whose only participants are the Ask agent and a chat account with a verified binding to the asking Member (any other direct message uses the guest or shared row) | the asking Member's view | the asking Member's Team and Organization Audiences |
  | Ask in the web GUI's Ask box, for the logged-in Member | the asking Member's view | the asking Member's Team and Organization Audiences |
  | Any other surface (a CI job's output, a new adapter) | Forge-public repos only, until an Admin defines its ceiling | none |

  **The PR comment is always narrow.** Forge access can widen before any sync sees it (a new outside collaborator reads existing comments at once), so a comment that lives on the Forge never holds more than Forge-public repos plus the Change Request's own repo. "That repo" is always allowed, because every reader of the Change Request can already read it on the Forge. The full cross-repo report, with impact on Open and Restricted repos and any Memories, sits behind a link from the comment to the web GUI, which computes it at read time for the signed-in human Member's own effective view. That is the human Member's own query, not a Service Agent's; a request authenticated as a Service Agent always carries its surface's ceiling, here as everywhere. The human's query carries no ceiling, is never cached across Members, and is not a published artifact. A reader without a Member login sees nothing behind the link. The comment, the link and its URL are the same whether or not anything lies beyond the ceiling, so neither the comment's existence nor its link reveals hidden impact. The table is exhaustive. Defining a ceiling for a new surface, and an Admin setting a chat-account binding for someone, are widenings; a Member binding their own chat account is a credential act, not a widening, except where it first makes a Restricted or Forge-private repo reachable through Ask ([ADR 0010](0010-ask-agent-and-chat-adapters.md)). A surface whose output persists where readership can widen before Yggdrasil notices (as with PR comments) gets a ceiling wider than Forge-public repos only if its output is checked at read time or Yggdrasil can remove it before the readership widens. Chat answers are the one stated exception: their rows below are wider, and their residue in a conversation's history is accepted (below). The Ask agent is not a Personal Agent, so it never recalls the asker's private overlay, even in a direct message. A ceiling protects only material retrieved under it, so a Service Agent composes each artifact from a context that holds only what it retrieved under that artifact's ceiling. Nothing retrieved for one destination is carried into another.

  Ceilings are evaluated when an artifact is posted, and again when a repo it drew on leaves its ceiling. PR impact comments are Yggdrasil's own and are already updated in place. The reporter is a built-in server principal whose own view is every admitted repo, always narrowed by the comment's ceiling, not an Admin-issued Service Agent ([ADR 0013](0013-pr-impact-report.md)), and its commit status carries nothing derived from impact: when a repo a live comment drew on leaves the Forge-public set or leaves admission, the reporter recomputes the affected comments. The check covers every revision of the comment a reader can still open, not only the current one: if any revision exceeds the current ceiling, the reporter deletes the comment and posts a new one, or redacts each such revision where the Forge allows it. It never relies on an edit alone, because Forges keep comment edit history readable. Chat answers live in another system's history. Whenever a Team-bound channel contains anyone who is not currently a Member of the bound Team, whether by joining the channel or by leaving the Team, the binding lapses, new answers fall back to the narrower ceiling, and Admins are warned. Past answers stay where they were posted: that residual exposure is accepted, not prevented.

  Hidden impact reaches the recipients above as a notice, never the shared artifact. How channel membership is checked belongs to the Ask agent's chat-adapter contract; how a repo's Forge visibility is read, and how the comment links to the web GUI report, belong to the PR impact report design. When the Forge cannot answer, the narrower ceiling applies.

### Memories

- **Memories need their Audience and every anchored repo.** A Member recalls a Memory only when they are in its Audience *and* every repo it is anchored to is in their effective view (below). This replaces ADR 0007's "recallable only while every repo it anchors to is still indexed" with "in the caller's view", and narrows its "attests the content is fit for org-wide view" to fitness for the chosen Audience. A reviewer of a Proposal must have every one of its anchored repos in their view. ADR 0007's anchoring obligation widens with this: a Memory must anchor every repo whose content it discloses, including repos that are Open or public on the Forge when it is written, so that a later restriction of any of them also hides the Memory.
- **Supersession is judged on the caller's chain.** Within a supersession chain, each caller gets the newest version they can recall, by Audience and effective view; any other version is *hidden* from them. Every head check on a write runs against the head the caller can recall. A write that supersedes a version with a hidden successor succeeds as a sibling of that successor, never as a refusal, so no refusal reveals a hidden successor. A caller who can see both sees the newer one.

### Sync and revocation

- **Revocation lag is bounded and fails closed.** Forge-derived memberships and grants converge within one stated sync interval. Forge webhooks speed this up where offered, and it never depends on them. An Admin may locally revoke any Forge-derived grant or membership, and a Team Maintainer any Forge-derived membership of their Team, with immediate effect. The local revoke overrides sync until it is cleared, by an Admin or by the Team Maintainer who made it. A Forge-derived grant or membership that sync has not reconfirmed within a maximum age lapses until sync succeeds again, so a long Forge outage degrades to less Visibility, never to stale access. Explicit Admin grants do not lapse. A repo's Forge visibility follows the same maximum age: if sync has not reconfirmed it, the repo counts as not Forge-public and drops out of every Forge-public ceiling (an existing PR comment is frozen rather than deleted, [ADR 0013](0013-pr-impact-report.md)). Its Open or Restricted state for Members is unchanged, and an Admin can set it to Restricted locally at once. The interval and maximum age will be set by the Identity and login ticket on the wayfinder map (#133) and then written into RFC 0001.

### Cursors and caches

- **Cursors and caches belong to one effective view.** A caller's *effective view* is:
  - their view, plus any active Break-glass Session;
  - intersected with their reader ceiling, which every Service Agent query has;
  - for Memory Verbs, together with the Audiences they may recall from.

  A cursor carries, or with ADR 0011 refers to server-held state carrying, the Member's id and a fingerprint of their effective view when it was issued. Presented by another Member, or after that effective view has changed, it is refused with the same error as an expired cursor. Only derived Verbs share result caches, keyed by the effective-view fingerprint, so two callers share an entry only when they see exactly the same repos under the same ceiling. Memory Verbs are never cached across Members. Revocation therefore needs no extra cursor or cache invalidation.

## Considered options

- **Keep ADR 0001's org-visible model and continue not indexing sensitive repos.** That is simplest, but it rules out Teams as a boundary and leaves the most sensitive code outside the brain.
- **Per-document ACLs inside the Shard** (research option B, the Onyx and Glean pattern). Path-level rules become possible, but every visibility change rewrites Shards, against ADR 0005. Within-repo IDF would also count hidden documents unless the scorer were rewritten.
- **Repo grants plus a path post-filter** (option C, Sourcegraph sub-repo permissions). Results over-fetch and paginate in loops, and within-repo scores can leak hidden content. Every Verb would need the hook. Path- and directory-level restriction is out of scope for this effort.
- **Mirroring each person's Forge permissions** instead of granting per Team. This needs per-person sync across three Forges, and outside collaborators and per-person exceptions turn into hidden visibility nobody manages in Yggdrasil.
- **Forbidding Admins from granting a Restricted repo to their own Teams or Service Agents.** An Admin can grant it to an empty Team and then join that Team, and the rule blocks legitimate setup in deployments with one Admin. Notifying the Owning Teams of every widening closes the silent path without either cost.
- **Allowing Restricted grants only to Forge-synced Teams.** Simpler, but every restricted group must then be modelled on the Forge. Notifying on local additions keeps local Teams useful.
- **Letting the publishing agent filter its own results**, or using the requester's view with a warning not to share. The first is a confused deputy that a prompt injection can turn; the second leaks the moment an answer is posted.
- **A wider PR comment for repos the Forge reports no outside readers for** ("Open repos plus that repo"). It keeps cross-repo impact inline, but Forge access widens before any sync can narrow the comment, so a newly added outside collaborator reads internal Symbols in the window. Narrow comments with the full report behind a read-time check have no window.
- **Retracting past chat answers when a channel's readership widens.** It depends on every chat platform letting the bot edit old messages, and it rewrites history under people. Re-checking only the PR reports Yggdrasil owns, and stating the chat residue, promises only what can be kept.
- **Forge-public repos only for every published artifact.** Safe, but useless for an Organization whose code is mostly private.
- **Redacting hidden results** ("3 results hidden") instead of dropping them. A count or a placeholder still discloses that hidden code exists and roughly where.
- **Keeping last-known grants through a Forge outage.** Nothing breaks, but revocation then waits on the Forge for as long as the outage lasts.
- **Cursors that hold positions only** and re-check visibility on every page. Correct only while every page and cache path remembers to re-check. Binding them to the Member's view fails closed by construction.

## Consequences

- Every admission check becomes a view check: target resolution, search fan-out, graph traversal across repos, Memory recall and the review queue. One function owns that answer.
- Impact, widening and Break-glass notices need a notification path; Service Agent queries need a reader ceiling that the server derives from the surface's adapter credential and enforces.
- Forge sync now carries access decisions. Its freshness becomes a stated objective, and its failure mode is less Visibility.
- RFC 0001 still describes the ADR 0001 model: §5.1's "while every repo it anchors to is indexed" and "fit for org-wide visibility", §3's restore rule and §10's ADR list. They are rewritten to this ADR in the map's RFC consolidation step; until then this ADR wins where they disagree.
